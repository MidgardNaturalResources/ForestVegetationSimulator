## Chapter 11 mechanisms (Case Management and Run-Time Behavior; column matching and data types)
Differences between the Database Extension user's guide (release 2025.4) and the code. The Rmd follows the code.
- Guide section 5.0 says a statement is not run when a substituted variable is not defined. In `DBSPRSSQL`, a scheduled statement with an undefined or unknown `%name%` has the token replaced by `NULL` and the statement still runs.
- Guide section 3.3 says a decimal value cannot be coded for an integer variable. `fsql3_colint` truncates a real value and reads the leading integer of a text value; it does not reject either.
- Guide section 5.0 says only user-defined Event Monitor variables are matched to result columns. `DBSEXECSQL` also creates a new Event Monitor variable (first 8 characters of the column name) for an unmatched column when the variable table has room.

Code concerns (not changed; confirmed with a scratch build of `DBSPRSSQL` unless noted).
- `%FVSCase%` inserts a blank before the CaseID (`' '//CASEID`), so a quoted token gives a value with a leading blank.
- In the `FVSCASE` branch of `DBSPRSSQL`, `KODE` is not set to 1. When `%FVSCase%` is the last token in the statement, `KODE` stays 0 and the statement fails with the parsing error (`WHERE C='%FVSCase%'` fails; `WHERE C='%FVSCase%' AND S='%StandID%'` succeeds).
- In `DBSCASE`, `INDEX(".KEY",KEYFNAME)` has its arguments in the reverse order, so the `.key` extension is not stripped from `KeywordFile` (about 85 percent; not run).
- `DBSERROR` calls `DBSCASE(1)`, and `ERRGRO` calls `DBSERROR` for warnings and errors. A run with no output switch on that issues a warning therefore appears to create the output database and a FVS_Cases row (about 70 percent; not run).
- The FVS_InvReference upgrade in `DBSREFERENCE` adds `LocationCode` but not `SDIType`, so an older table without `SDIType` would fail on insert (about 70 percent; not run).
- Table upgrades exist only for `SCuFt` (tree list, cut list, ATRTList), FVS_Compute variables and `LocationCode`. No other column added in later releases is added to an existing table.

Existing Chapter 11 text to review.
- The UUID Generation section says the routine guarantees uniqueness; `UUIDGEN` produces a version 4 UUID from pseudo-random numbers, which makes a repeat improbable but is not a guarantee.
- The keyword example near the end of the chapter still lists FVS_DM_TreeList.

- Correction of an earlier entry: the claim that no call closes the databases at the end of a normal run was wrong. `DBSCLOSE` is called from `FILClose` (an entry in `FILOPN`), `DBSOPEN`, `DBSCHPUT` and `DBSPPGET`. `FILClose` is called by `fvsSetRtnCode` for any nonzero code (`INITRE` sets 2 when it reads `STOP`; `ERRGRO` and `RCDSET` also set codes) and by `fvsSetCmdLine` when the return code or restart code is nonzero. The databases are closed when the call to FVS after the last stand reads `STOP` (or the end of the keyword file, which also writes error FVS02 and sets the exit status through `ICCODE`).
- When a stand finishes, `fvsStopPoint(-1)` sets restart code 100 and FVS returns code 0, so the connections stay open. The `rFVS` function `fvsRun()` (FVSInterface repository, `rFVS/R/fvsRun.R`) breaks out of its loop when the restart code is nonzero, so it returns 0 after each stand and returns 2 only on the following call. The `fvsOL` custom run scripts break at restart code 100 ("end of current stand") and return 0. `fvsInteractRun()` loops until the return code is nonzero and so closes the databases. The explanation for open database handles after a completed `fvsRun()` rests on reading the code (about 90 percent); it was not run because R is not installed in the environment.
- `fvsLoad()` in `rFVS` calls `dyn.unload` on a previously loaded library without closing the databases first. Unloading the library does not release the SQLite file in the Windows environment (reported by the project owner); the code has no unload hook that closes the connections.
- The `fvsRun()` documentation in `rFVS` describes return code 2 as "finished processing all the stands". The code returns 2 only on the call after the last stand, not on the call that finishes it.
- `DBSINIT` turns off every output switch at the start of each stand, so output keywords must be read for each stand (consistent with the documented per-stand keyword records).

Code update ideas: control of the number of tree records per plot created by PLANT and NATURAL (not implemented; for discussion):
- Current behavior: for each request and each plot copy, the number of records is m = INT(PTREE/10 + 1) and each record has PROB = PTREE/m (`estb/estab.f:1374-1411`, `strp/estab.f:589-625`). The total is about (number of plots) x DUP x m, where DUP comes from MINREP (50 by default; MINPLOTS sets it, with a minimum of 20; `estb/esin.f:587-588`). The constant 10 and the minimum of 20 cannot be changed by the user.
- Field availability: PLANT and NATURAL use fields 1 to 7 (date, species, trees per acre, survival, age, height, shade code; `estb/esin.f:206-243`) and store six parameters with `OPNEW(KODE,IDT,IACTK,6,ARRAY(2))` (`esin.f:235`). The keyword reader accepts up to 12 fields on a 130-character record (`base/keyrdr.f:36,104`), so fields 8 to 12 are free.
- Option A, field 8 of PLANT and NATURAL = maximum trees per acre per record (default 10): m = INT(PTREE/field8 + 1). A default of 10 reproduces the current results. It is set per request, so species can differ. A larger value gives fewer records, but it cannot reduce the count below one record per plot copy.
- Option B, field 8 of PLANT and NATURAL = number of records per plot copy: m is set directly and PROB = PTREE/m. This is the most direct control, but a small m can give a large PROB per record, and there is no ceiling on that value. A and B would use the same field, so only one of them can be field 8 unless the other uses field 9.
- Mechanics common to A and B: raise the parameter count in OPNEW from 6 to 7; in ESTAB, test NP from OPGET so activity records with six parameters take the default (the `OPGET(...,6,...)` calls are at `estb/estab.f:416,976,1482`); the climate extension adds PLANT and NATURAL activities with six parameters (`clim/base/clauestb.f:232`) and would take the default.
- Files: `estb/esin.f` and `estb/estab.f` (AK, CI, EM, IE, KT); `strp/esin.f` and `strp/estab.f` (the partial model of OC, OP and 15 other variants); `metric/strp/estab.f` (BC and ON). The documentation was written from `estb/estab.f`; `strp/estab.f` has the same PTREE and IBRKUP lines, but the rest of it was not compared.
- Per-request fields (A or B) are preferred over a separate keyword for per-request control. Global controls (a lower MINPLOTS minimum, skipping plot replication when only planting is requested, or a cap on records per call that raises the trees per acre per record until the total fits) would follow the pattern of MINPLOTS and PASSALL and need a separate keyword or a changed minimum. This recommendation is about 70 percent likely to be the best fit; it was not tested.
- Risks: changing m changes PROB per record and therefore later growth and mortality, so results must be checked against the saved baselines in `tests/`; a default that reproduces the current output makes that check simple.
